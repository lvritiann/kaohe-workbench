## 第 0 章 十分钟看懂这个系统

一句话：**检查人拿手机打分，分数和三张照片自动写进金山表格；月底跑一个 PY 脚本，把明细折算成 28 分制落进考核记录表；另有一个定时脚本每天早上把销售日报算成人效推到网页看板。**

三条链路彼此独立，互不依赖，坏一条不影响另外两条：

```
链路一（打分落表，每天可能用）
  手机 score.html ──POST──> 腾讯云函数 ──轮询──> 金山 AirScript（score_write.js）
                                                   └─> 数据源表「检查明细」19 列

链路二（月度汇总，每月 1 次）
  数据源表「检查明细」 ──PY 脚本（金山 PY 编辑器）──> 考核记录_2026/2027.xlsx
                                                        └─> 每月 sheet × 30 个站块

链路三（人效看板，每天早上 5 次）
  金山销售日报 ──AirScript 定时任务（eff_push.js）──> GitHub docs/data/efficiency.json
                                                        └─> eff.html 人效看板
```

**为什么是这套架构，而不是「自己写个后端 + 数据库」：**

| 约束 | 结论 |
|---|---|
| 检查人只有十几台手机，不可能装机、不可能教 | 必须零配置，打开网页就能用 |
| 数据要落在金山表格里，科室要能直接在表上核 | 表格是唯一台账，不能另建数据库 |
| 没有服务器、没有预算、没有 IT 运维 | 只能用免运维的云函数 + 表格自带脚本 |
| 照片要能看，不能只存链接 | 必须走「图片嵌进单元格」 |

腾讯云函数 + 金山 AirScript 的组合，恰好是「无服务器 + 台账即数据库」最省的一种拼法：
云函数只做转发（不存任何数据），AirScript 只做写表（不暴露任何接口给外部）。全链路一年成本不到 1 元。

## 第 2 章 业务口径（V6 计分规则）

> **红线：现在全网只认 V6。仓库里任何「三段加权」「56/28」「基准 65」「少扣多奖」「90/80/70/60 等级制」都是历史稿，一律作废。**
> 规则源：《高速公路加油站目标责任考核方案》V1.0（2026-11-16 定稿）
> 代码上的唯一规则源：`docs/assets/config.js`

### 2.1 四段分值

| 段 | 项目 | 基准 | 封顶 | 算法 |
|---|---|---|---|---|
| 一 | 油品销量 | 40 | 50 | 40 × 完成率，完成率 ≥125% 封顶 |
| 二 | 非油销量 | 10 | 12 | 销售 5 + 毛利 5，各封顶 6（完成率 ≥120% 封顶） |
| 三 | 油品人效 | 12 | 20 | 人效 ≤49：12×人效÷49；>49：12+8×(人效−49)÷49 |
| 四 | 现场管理段 | 38 | 38 | 一级考核 5 + 二级运营检查 28 + 神秘访客 5 |

```
综合得分 = 油品段 + 非油段 + 人效段 + 现场管理段 − 投诉扣分 + 进步加分
基准 100，封顶 120，不设等级，只出 1–15 名（同分油品段高者排前）
```

### 2.2 关键参数（不得擅改）

| 参数 | 值 | 依据 |
|---|---|---|
| SGE 汽油 | **39** /吨 | 1360 升 ÷ 34.75 升/单 ≈ 39 单，一台一份 |
| SGE 柴油 | **27** /吨 | 1200 升 ÷ 153.35 升/单 ≈ 7.82 单 × 3.5 台 ≈ 27.4 取 27 |
| 基准人效 | **49** | 15 站算术平均 49.26 取整，当年固定、一年一核 |
| 扣减人数 | **4 人** | 24h 两班倒、每班至少 2 人的最低开班配置 |
| 人效段基准/冲击/封顶 | 12 / 8 / 20 | 人效=2 倍基准（98）封顶 |
| 二级检查总分 | 100 分制 **80 项** → **28 分** | |
| 一级考核 | 5 分（百分制折算） | 每年一次随机抽查，未开展记 NA |
| 神秘访客 | 5 分 | 南沙不参与，按 NA 规则折算补齐 |
| 投诉扣分 | 升级 10 / 重复 20 / 监管或媒体 50 | 不设下限；重大投诉一票否决 |
| 进步加分 | 年度人效同比每升 1% 加 0.2，上限 3 | 不参与月度排名 |

### 2.3 会计月（最容易写错的一条）

```
会计月 = 上月 26 日 — 本月 25 日
天数按实计：28 / 29 / 30 / 31（3 月会计月最短：平年 28 天，闰年 29 天）
26 日及以后 → 算下个月会计月
跨年分界点 = 12 月 26 日（12/26 起的检查落次年 01 月 sheet）
```

代码里任何地方**都不得把天数写死成 30 或 31**：
- 浏览器端 `Engine.accountDays('YYYY-MM')`
- Python 端 `period_of()` / `account_days()`
- AirScript 用会计月日期差

月中滚动用「已计天数」（`period.elapsed`），月末自然等于整月天数。

### 2.4 人效公式

```
人效 = (会计月累计当量 ÷ 已计天数) ÷ (月均在岗 − 4)
当量 SGE = 汽油吨 × 39 + 柴油吨 × 27
月均在岗 = 各日在岗之和 ÷ 已计天数

★ 人效只有一个数源：docs/data/efficiency.json
  排名页、计算页、人效看板三处同源同值。
★ 当量口径含批发（2026-11-17 定案 A 案）：取数与销售日报一致，
  即「现金+POS+微信+支付宝+工贸卡+壳牌卡+大客户+定期结算」，不做零售/批发拆分。
  后果已知并接受：省界站（南沙、华山）大客户柴油占比高，人效天然居前。
★ stations.json 里的三年平均日均吨是参考值，不参与计分。
```

### 3.1 端到端时序

```
手机 score.html          SCF kaohe-relay           金山 AirScript
     │                        │                         │
     │ ①POST /               │                         │
     │  {Context:{argv:{      │                         │
     │   payload:{…}}}}       │                         │
     ├───────────────────────>│                         │
     │                        │ ②POST …/script/{sid}/task
     │                        ├────────────────────────>│
     │                        │<── {task_id:"xxx"} ─────┤  毫秒级
     │                        │                         │  （脚本开始跑）
     │                        │ ③GET /api/v3/script/task?task_id=xxx

     │                        │<── {status:"running"} ──┤
     │                        │      …0.7s→1.05s→1.6s→2.4s→3s…
```

**为什么绕这一圈而不是手机直连金山：**

| | 手机直连金山 | 走 SCF 中转（现方案） |
|---|---|---|
| 每台手机要填什么 | webhook + **账号级令牌** | 什么都不填 |
| 配几次 | 十几台各配一次 | 服务器配一次，全员生效 |
| 某台手机丢了 | 那串令牌能读写名下**全部**金山文档 | 最多被刷几次提交 |
| 跨域 | 实测通的，但受浏览器内核影响 | 函数自己返跨域头，稳定 |

前端靠一个字符串判断走哪条路：地址里有没有 `/api/v3/ide/`。
有 = 直连（带 `AirScript-Token` 头）；没有 = 走中转（什么都不带）。见 `docs/assets/score.js:882`。

**请求**

**为什么 `items` 必须传全 80 项**：脚本需要全部标准分才能凑出分母 100。只传扣分项的话折算分永远算错（分母凑不出 100）。

**响应**

```json
{
  "data": { "result": "{\"ok\":true,\"station\":\"韩城东\",\"month\":\"2026-11\",
                        \"rows\":3,\"photos\":3,\"mode\":\"cell\",
                        \"converted\":96.3,\"op\":26.96,\"log\":[\"…\"]}" },
  "status": "finished",
  "error": ""
}
```

前端拿 `data.result` 二次 `JSON.parse`（它可能是字符串也可能已是对象），然后按 `inner.ok` / `inner.pending` 分支。

**三种结果状态（关键设计）**

| 状态 | 触发条件 | 页面表现 | 草稿 |
|---|---|---|---|
| `ok: true` | 脚本 return 成功 | 「已落表」+ 折算/运营段/行数/张数 | 清除 |
| `pending: true` | 轮询预算用完 / `errno:10000` | 「已提交 · 结果未确认」（黄，不是红） | **保留** |
| `ok: false` | 脚本自身报错 | 红色失败 + 日志 | 保留 |

> `pending` 这个中间态是整个设计的要点：金山 `sync_task` 是同步接口，脚本一重就回 `errno:10000 / "Unavailable"`，**但脚本其实执行成功了**。报「失败」会让人重复提交。所以宁可报「未确认」。

### 3.3 腾讯云函数（SCF）工作原理与写法

#### 3.3.1 SCF 是什么

腾讯云云函数（Serverless Cloud Function）是**事件驱动的函数托管服务**：
你只上传一段代码，不买服务器、不配 Nginx、不管进程守护；平台负责拉起容器、把请求变成 `event` 对象喂给你的函数、把返回值变成 HTTP 响应。

术语对照：

| 概念 | 含义 | 我们的取值 |
|---|---|---|
| 函数（Function） | 一段可被调用的代码 | `kaohe-relay` |
| 运行环境 | 预装的语言运行时 | **Node.js 24.11**（LTS 到 2028-04） |
| 入口方法（Handler） | 平台调哪个函数 | `index.main_handler`（文件名.函数名） |
| 事件函数 | 由事件触发、返回结构化响应 | 我们用的就是这种 |
| 函数 URL | 给函数一个固定 HTTPS 域名 | `https://1320695126-…tencentscf.com` |
| 环境变量 | 注入到 `process.env` 的配置 | `KDOCS_URL` / `KDOCS_TOKEN` / `ASYNC_POLL_SEC` |
| 执行超时 | 单次调用最长能跑多久 | **120 秒**（可选 1~900） |
| 地域 | 机房位置 | 广州（`ap-guangzhou`） |

**选 Node 24.11 的理由**：24 和 22 都是 LTS，24 多一年维护期；20.19（2026-03 EOL）和 18.15（2025-03 EOL）已过生命周期，迟早被下架强制迁移。本代码只用 `https`/`http`/`url`/`Buffer`/`async-await`，四个版本全支持，选新无兼容风险。

#### 3.3.2 函数签名与事件结构（这是「怎么写」的核心）

```js
exports.main_handler = async (event, context) => {
  // event   = 请求
  // context = 运行时信息
  return { statusCode, headers, body, isBase64Encoded };
};
```

**`event` 长什么样**（函数 URL 的 HTTP 集成）：

```js
{
  httpMethod: "POST",                  // 或 event.requestContext.httpMethod
  headers: { origin: "https://lvritiann.github.io", ... },  // ★ 全小写键
  body: "{\"Context\":{...}}",         // 字符串，不是对象
  isBase64Encoded: false,              // 平台可能 base64 包装
  requestContext: { ... }
}
```

三处必须做的防御：

```js
// ① 方法名大小写不定、字段位置不定
const method = (event.httpMethod ||
  (event.requestContext && event.requestContext.httpMethod) || 'POST').toUpperCase();

// ② origin 键可能大小写都有
const origin = (event.headers &&
  (event.headers.origin || event.headers.Origin)) || '';

// ③ body 可能被 base64 包过（平台行为随配置变），必须两级判断
let body = event.body || '';
if (event.isBase64Encoded ||
    (event.isBase64Encoded === undefined &&
     /^[A-Za-z0-9+/=\s]+$/.test(body) && body.length > 200)) {
  try { body = Buffer.from(body, 'base64').toString('utf8'); } catch (e) {}
}
```

**返回格式**（必须严格是这个四件套，少一个就 502）：

```js
{
  statusCode: 200,                    // HTTP 状态码，必须是数字
  headers: { 'Access-Control-Allow-Origin': '*', 'Content-Type': 'application/json;charset=utf-8' },
  body: JSON.stringify(obj),          // 必须是字符串
  isBase64Encoded: false              // 必须是布尔
}
```

#### 3.3.3 `context` 的时间字段（腾讯云特有的坑）

要在函数里「还剩多少时间可用」，有两个可能的字段，**腾讯云只提供第二个**：

| 字段 | 出处 | 腾讯云实测 |
|---|---|---|
| `context.getRemainingTimeInMillis()` | AWS Lambda 系惯例，很多文档照抄 | **不存在** |
| `context.time_limit_in_ms` | 腾讯云 SCF 真正提供的「配置的执行超时」 | 存在（如 `120000`） |

```js
function totalBudgetMs(context, t0) {
  try {
    // 优先：直接给剩余时间
    if (context && typeof context.getRemainingTimeInMillis === 'function')
      return Number(context.getRemainingTimeInMillis()) || 0;
    // 腾讯云：给的是总上限，得自己减已耗时
    if (context && typeof context.time_limit_in_ms === 'number' && context.time_limit_in_ms > 0)
      return Math.max(0, context.time_limit_in_ms - (Date.now() - t0));
  } catch (e) {}
  return 0;   // 都取不到 → 调用方用兜底值
}
```

> **血泪教训**：v1.9 那版只写了 `getRemainingTimeInMillis`，线上跑起来 `pollSec` 永远是 45（兜底值），自动预算完全失效，但因为不报错，谁也没发现。后来在健康检查里加了 `env` 字段自诊断才查出来。
> **教训**：凡「依赖运行时提供的字段」，必须能被观察到。所以健康检查返回：
> ```json
> {"ok":true,"version":"2.0-async","hasTarget":true,"hasToken":true,
>  "pollSec":110,"env":{"hasRemain":false,"timeLimitMs":120000}}
> ```

#### 3.3.4 为什么用「函数 URL」而不是「API 网关触发器」

| | API 网关触发器 | 函数 URL（现方案） |
|---|---|---|
| 产品状态 | **2025-06-30 停止服务，2024-07-01 起禁止新建** | 正常可用 |
| 超时 | 网关层 15 秒，要单独去网关控制台改 | **直接用函数自身超时** |
| 跨域头 | 要勾「集成响应」，否则被吞 | 默认透传 |
| 配置步骤 | 建 API 服务 + 建触发器 + 改超时 | 点一下「新建函数 URL」 |

函数 URL 的四项配置：

| 项 | 值 | 理由 |
|---|---|---|
| 别名/版本 | **`$LATEST`** | 绑具体版本号的话，改了代码不生效 |
| 公网访问 | 开启 | 手机在 4G/5G 上访问 |
| **CORS** | **关闭** | 函数自己返跨域头，两边都开会变成 `contains multiple values`，比没头还难查 |
| 授权类型 | **开放** | 选 CAM 鉴权手机调不动 |

> 函数 URL 响应会带 `Content-Disposition: attachment`（平台加的），浏览器直接打开会下载文件。前端 `fetch` 不受影响，不用管。

#### 3.3.5 中转的核心算法：异步提交 + 轮询

**背景**：金山 `sync_task` 是同步接口。脚本重（写多行 + `Range.InsertImage` 嵌图）时会返回

```json
{"errno":10000,"msg":"","reason":"","result":"Unavailable"}
```

**而脚本本身是执行成功的** —— 于是出现「表里有数据、页面报没能落表」这种最误导人的状态，现场的人一看红字就会再交一遍。

**解法**：改走官方异步接口。

```
① POST {origin}/api/v3/ide/file/{fileId}/script/{sid}/task
   ← 毫秒级返回 {task_id: "xxx"}，不等脚本

② GET  {origin}/api/v3/script/task?task_id=xxx
   ← 轮询，直到 {status: "finished" | "failed" | "error"}

③ 把最终结果原样回给页面（信封形状与 sync_task 一致，前端解析代码一行不改）
```

**端点推导**（只配一个 `KDOCS_URL`，另外两个在代码里就地替换路径段）：

```js
function endpoint(kind, taskId) {
  const u = new URL(KDOCS_URL);
  if (kind === 'task') {
    // …/script/{sid}/sync_task  →  …/script/{sid}/task
    u.pathname = u.pathname.replace(/\/sync_task\/?$/, '/task');
    return u.toString();
  }
  if (kind === 'poll') {
    // https://{origin}/api/v3/script/task?task_id=xxx
    const p = new URL(u.origin + '/api/v3/script/task');
    p.searchParams.set('task_id', taskId);
    return p.toString();
  }
  return u.toString();   // sync = 原样
}
```

**轮询预算与退避**：

```js
const POLL_SAFETY_MS = 5000;   // 留 5 秒回包余量

function pollBudget(context, t0) {
  const total = totalBudgetMs(context, t0);
  let budget;
  if (total > 0) {
    const left = total - POLL_SAFETY_MS;
    // ASYNC_POLL_SEC 填正数 → 作为上限，永不被自动值顶破
    budget = POLL_CAP_MS > 0 ? Math.min(POLL_CAP_MS, left) : left;
  } else {
    budget = POLL_CAP_MS > 0 ? POLL_CAP_MS : 45000;   // 兜底
  }
  return Math.max(1500, budget);   // 最少给 1.5 秒，否则等于不轮询
}

async function pollUntilDone(taskId, budgetMs) {
  const deadline = Date.now() + budgetMs;
  let delay = 700;
  while (Date.now() < deadline) {
    // ★ 别让退避越过截止时间：最后一跳最多睡到 deadline 为止
    const left = deadline - Date.now();
    await sleep(Math.min(delay, Math.max(0, left)));
    delay = Math.min(Math.round(delay * 1.5), 3000);   // 指数退避，封顶 3 秒
    const r = await requestJson('GET', endpoint('poll', taskId), null);
    const j = tryJson(r.text);
    const st = j && j.status;
    if (st === 'finished' || st === 'failed' || st === 'error') return j;
  }
  return null;   // 超时
}
```

**三层兜底**：

| 情况 | 行为 |
|---|---|
| 异步接口不可用（老账号/接口变更） | 自动退回 `sync_task`，行为与旧版一致 |
| 轮询把预算用完 | 返回 `pending:true`，页面显示「已提交 · 结果未确认」 |
| 函数仍回 `errno:10000` | 前端也认这个特征，同样按「未确认」处理 |

#### 3.3.6 超时怎么定（两端必须配套）

| 环节 | 值 | 位置 |
|---|---|---|
| 函数执行超时 | **120 秒** | 腾讯云控制台 → 函数配置 |
| 轮询预算 | `min(ASYNC_POLL_SEC=110, 120−5=115)` = **110 秒** | 环境变量 |
| 单次 HTTP 请求超时 | 20 秒 | `TIMEOUT_SEC`（默认值） |
| 手机端等待上限 | **150 秒** | `docs/assets/score.js` 的 `CLIENT_WAIT_MS` |

```
120（函数） < 110（轮询，留 10 秒回包） < 150（客户端，留 40 秒网络余量）
```

> **要往上加必须两边一起改**，否则函数等得比页面久，等于白等。SCF 上限 900 秒。

#### 3.3.7 请求体大小限制链

```
单张照片代码里硬压到 ≤ 500KB（长边 1600px，质量 0.82→0.5 逐档降，最多 4 轮）
   ↓ base64 膨胀 1/3
前端提交闸 body ≤ 5MB        ← docs/assets/score.js，超出弹「照片太多」
   ↓
SCF 同步请求事件硬限 6MB      ← 腾讯云文档 Sync request event size 6 MB
   ↓
函数内再兜一次 10MB 检查       ← 超过返 413，免得徒劳转发
```

5MB body ≈ 3.7MB 原始照片 ≈ 7 张 500KB 的图。再多就得删图或分两次提交（同站同月以最新为准）。

#### 3.3.9 打包脚本为什么必须存在

```python

                                                          # ② 整包替换，连带清掉 index.mjs
```

- **③ 字节可比对**。同样源码每次打出来的包完全一致，能判断「这次部署的是不是我以为的那份」。

#### 3.4.7 三个必须理解的实现细节

**① 月份必须归一，否则永远替换不掉旧行**

A 列只要被 WPS 识别成日期，读回来就是**数值序列号**（如 `46327`）或 `Date` 对象，直接拿字符串比会永不相等 → 同一站同一月越提越多行。

```js
function normMonth(v) {
  if (v === null || v === undefined) return '';
  if (typeof v === 'number') {
    if (v < 40000 || v > 55000) return String(v);          // 46000~50000 才是合理日期区间
    var d = new Date(Date.UTC(1899,11,30) + Math.round(v)*86400000);
    return d.getUTCFullYear() + '-' + pad(d.getUTCMonth()+1);
  }
  if (Object.prototype.toString.call(v) === '[object Date]')
    return v.getFullYear() + '-' + pad(v.getMonth()+1);
  var m = /^(\d{4})[-\/.](\d{1,2})/.exec(String(v).trim());
  if (m) return m[1] + '-' + pad(Number(m[2]));
  return String(v).trim();
}
```

配套：写之前先 `sh.Range('A2:A'+end).NumberFormat = '@'` 把 A 列设成文本。

**② 必须逐行赋值，整片二维数组只认第一行**

```js
// ❌ 错：这样写只落第一行，其余静默消失，且不报错
sh.Range('A2:S' + n).Value2 = rows;

// ✅ 对：每行一次单行赋值
for (var ri = 0; ri < rows.length; ri++) {
  try { sh.Range('A'+(2+ri)+':S'+(2+ri)).Value2 = [rows[ri]]; okRow++; }
  catch (e) { badRow.push(2+ri); }
}
```

**症状**：一次提交 2～3 个扣分项，脚本报「已写 3 行」，表里却只剩第 1 行。只提交 1 项时正常。
**为什么沙盘测不出来**：本地 mock 的 `Range` 是普通赋值，永远成功。**这个 bug 只能在真表上暴露。**

**③ 行号必须在内存里算，不能写完再回读**

```js
// ★ 记录每条新行落在第几行。不能「写完再读回来找行号」——
//   AirScript 里刚赋完值立刻读同一区域，某些版本返回的还是旧值（空），
//   导致插图循环一条都匹配不上、数量恒为 0，而且不报错。
var placed = [];
// … rows.push([...]); placed.push({ row: rows.length + 1, key: String(it.no) });
```

#### 3.4.8 照片怎么进单元格（技术选型的关键决策）

两条路都试过，结论明确：

| | `=IMAGE(公网直链)` | **`Range.InsertImage(base64)`**（现方案） |
|---|---|---|
| 图片要公网地址 | 要（得先传图床） | **不要** |
| 要文档授权 | 要，且实测一直卡 `#BLOCKED!` | **不要** |
| 要多带一份 GitHub 令牌 | 要 | **不要** |
| 传输路径 | 手机→金山→GitHub→金山 | **手机→金山，直达** |
| 表格里是 | 公式，失败就是一串字 | **真图片，嵌在格子里** |

```js
// 写文字和写图必须分两步：Value2 批量赋值会把图片数据当普通文本存进去
function writeImages(pics, placed) {
  for (var i = 0; i < placed.length; i++) {
    var rowNo = placed[i].row;
    var it = pics[placed[i].key];
    if (!it || !it.src) continue;
    sh.Range('N' + rowNo).Clear();          // 先清，重复提交时格子里可能压着旧图
    sh.Range('N' + rowNo).InsertImage(it.src);   // it.src = 'data:image/jpeg;base64,…'
  }
}
```

**已知代价（2026-11-19 明确接受）**：图片存进表格文件本身，表格会随月份累积变大。

| 假设 | 数值 |
|---|---|
| 一站一次检查扣分项 | 约 10 项 → 10 张图 |
| 15 站一个月 | 约 150 张 |
| 单张上限 | 500KB |
| 每月增量 | 约 45MB |
| 一年累计 | 约 540MB |

金山在线表格到几百 MB 会明显变卡。**要改只动一个常量**：`docs/assets/score.js` 的 `PHOTO_MAX_BYTE = 500*1024`，改成 `150*1024` 即 150KB，改完手机强刷一次（缓存版本号要跟着升）。已进表的老图不会变小。

**回退开关**：`score_write.js` 第 57 行 `PHOTO_MODE: 'cell'`，改成 `'url'` 就退回 `=IMAGE` 老路（前提是 GitHub 令牌和 IMAGE 授权都还在）。若脚本报 `InsertImage is not a function`（客户端版本太老），就改这个。

**覆盖**：同站同月重复提交以最新一次为准。


**占位**：检查了但零扣分，必须写一行占位。


**为什么不能省**：`record_sync.py` 靠「明细里有没有这个站这个月」判断「满分」还是「未检查」。没有占位行 → 判为未检查 → 整块留空 → 该站**白丢 28 分**。

#### 3.4.10 计分算法（三处必须逐位一致）

`score_write.js` 的 `computeScore()`、`engine.js` 的 `inspectResult()`、`record_sync.py` 的 `_fill_block()` 是**同一套口径的三份实现**，改一处必须三处同改：

```
effective = 100 − NA 项标准分之和              ← NA 项不进分母，也不进得分
converted = 实得分 ÷ effective × 100
运营段    = converted ÷ 100 × 28，封顶 28
一票否决  → 当期综合记 0（序号 'v3' 不进分母、不参与 80 项计分）
```

```js
function computeScore(p) {
  var total = 0, na = 0, got = 0;
  for (…) {
    total += std;
    if (res === 'na') { na += std; continue; }               // 不进分母
    if (res === 'no' || res === '否' || res === '扣分') continue;  // 得 0
    got += std;                                              // 符合
  }
  var eff = total - na;
  var conv = eff > 0 ? r2(got / eff * 100) : 0;
  var op = Math.min(r2(conv / 100 * 28), 28);
  if (Math.abs(total - 100) > 0.01) say('⚠️ 检查项标准分合计 ' + total + '（应为 100），题库可能被改过');
  return { total, na, raw: r2(got), converted: conv, op };
}
```

| `g.Application` vs `Application` | **读明细用 `g.Application`**（那个簿的 Application）；**写记录表用全局 `Application`**（本簿）。混用会写错文件 |
| `Range("A1:S3000").Value2` | 一次取回，返回二维元组；比逐格读快几百倍 |
| `Workbooks.Close()` | 必须放 `finally`，否则打开失败会留下句柄，下次读到旧快照 |

**步骤 2：把二维表聚合成本脚本要用的结构**

```python
def _collect(rows):
    """→ rec[(站,月)] = {序号: (得分, 结果, 说明, 照片文件名, 照片附件ID)}
       meta[(站,月)] = (检查人, 检查日期, 否决串)
       months        = 明细里出现过的会计月集合
       dropped       = 因表类型不在白名单被丢弃的 (月, 站, 表类型)"""
    rec, meta, months, dropped = {}, {}, set(), []
    for r in rows[1:]:                       # rows[0] 是表头，跳过
        m  = _norm_month(_cell(r, 0))        # A 列月份
        st = str(_cell(r, 1) or "").strip()  # B 列站名
        if not m or not st:                  # 空行 / 合计行
            continue
        typ = str(_cell(r, 2) or "").strip() # C 列表类型
        if typ not in ACCEPT_TYPES:          # 只认 ""、运营检查、二级运营检查
            dropped.append((m, st, typ))
            continue
        months.add(m)
        key = (st, m)

        # ★ meta 对**每一行**都登记（含序号为空的占位行）
        #   所以「检查过但零扣分」一定在 meta 里留痕 —— main() 靠这个区分未检查和满分
        meta[key] = (检查人, 检查日期, 去重后的否决串)

        no = _cell(r, 3)                     # D 列序号
        if no in (None, ""): continue        # 占位行：只登记 meta，不参与计分
        try:    no = int(no)
        except: continue                     # 'v3' 等否决序号：只贡献否决文本，不参与计分

        rec.setdefault(key, {})[no] = (
            _cell(r,7),                      # H 得分
            str(_cell(r,8) or "").strip() or "扣分",   # I 结果
            _cell(r,9),                      # J 说明
            _cell(r,12),                     # M 照片文件名
            _cell(r,13),                     # N 照片附件ID
        )
    return rec, meta, months, dropped
```

**这几个返回值各自解决什么问题**：

| 返回值 | 解决什么 |
|---|---|
| `rec` | 每个站每个月有哪些项被扣/NA，以及各自的结果 |
| `meta` | 这个站这个月**到底检查过没有**（关键判据） |
| `months` | 明细里有哪几个月，用来和「当前会计月」对账 |
| `dropped` | 表类型填错的行（如错填「神秘访客」），要单独报错而不是当「没人填」 |

**月份归一（PY 版）**：

```python
def _norm_month(v):
    """'2026-11' / 日期时间对象 / '2026/11' / 202611 数字 全部归一成 'YYYY-MM'。
    不归一会导致键永远匹配不上，30 站全静默跳过（看着像跑成功了）。"""
    if v is None: return ""
    if hasattr(v, "year") and hasattr(v, "month"):
        return "%04d-%02d" % (v.year, v.month)
    s = str(v).strip()
    if len(s) >= 7 and s[4] in "-/." and s[:4].isdigit() and s[5:7].isdigit():
        return "%s-%s" % (s[:4], s[5:7])
    digits = "".join(ch for ch in s if ch.isdigit())
    if len(digits) == 6:
        return "%s-%s" % (digits[:4], digits[4:6])
    return s
```

**否决串去重**：`read_check_zip.py` 把「一票否决项」文本写进了该站**每一行**明细，逐行拼接会变成「散装汽油销售管控；散装汽油销售管控；散装汽油销售管控」。按分号拆开保序去重，旧包也能自我纠正。

### 4.4 记录表的块结构（写脚本前必看）

```
一块 = 标题 1 + 信息 1 + 列头 1 + 明细 N 项 + 合计 1 + 尾行 1
     N=73 时 78 行（旧）；N=80 时 85 行（新，2026-12 起）

r0        A 列含「二级运营检查记录」的标题行 ← 探测锚点
r0+1      信息行：A:B 站名 / C:D 会计月 / E:F 检查人 / G:H 检查日期 / I 生成时间
r0+2      列头
r0+3 …    明细项（A序号 B大类 C项目 D标准分 E得分 F结果 G说明 H照片文件名 I照片附件ID）
```

★ **明细项数不是常数**。旧题库 73 项、新题库（8.21 表）80 项，两者并存：

| | 旧块（73 项） | 新块（80 项） |
|---|---|---|
| 明细区间 | r0+3 … r0+75 | r0+3 … r0+82 |
| 合计行 | r0+76 | r0+83 |
| 尾行 | r0+77 | r0+84 |
| 块高（无空行） | 78 | **85** |
| 块步长（年度表带分页空行） | 79 | **86** |

| 项 | 值 |
|---|---|
| 块起点 | 运行时扫 A 列含「二级运营检查记录」的标题行**自动探测**，不写死 |
| 明细区间 | **逐块探测**：找 A 列「合计」行 → 明细 = r0+3 至 合计行−1；找不到就退化为「块内最后一个整数序号行 +2」 |

### 4.5 逐块填分：`_fill_block`

```python
def _fill_block(ws, r0, dct, a, b):
    """写一块的 E:I 列（得分/结果/说明/照片文件名/照片附件ID）
    a/b 由 _block_layout 逐块探测传入，不假定 73 或 80
    → (折算分, 运营段得分, 消费掉的序号集合, 结果与得分矛盾项数)"""
    block = ws.Range("A%d:D%d" % (a, b)).Value2 or ()   # 只读 A:D（序号+标准分）
    out, got, na, total = [], 0.0, 0.0, 0.0
    used = set()
    for row in block:
        no, std = row[0], _num(row[3])
        total += std
        if no in dct:                       # 明细里有这一项
            sc, res, note, photo, pid = dct[no]
            if res.upper() == "NA":
                na += std;  out.append(["NA","NA",note,photo,pid]);  continue
            if res in OK_WORDS:  score = std
            elif sc is not None and 0 < sc < std:  score = sc     # 手工部分得分
            else:                score = 0.0
            got += score
            out.append([score, res or "扣分", note, photo, pid])
        else:                               # 明细里没有这一项 = 没被挑出毛病
            got += std
            out.append([std, "符合", "", "", ""])
    ws.Range("E%d:I%d" % (a, b)).Value2 = out    # 一次写 5 列 × N 行（单块内可整片写）
    eff  = total - na
    conv = round(got / eff * 100.0, 2) if eff > 0 else 0.0
    op   = min(round(conv / 100.0 * INSPECT_BASE, 2), INSPECT_BASE)   # INSPECT_BASE = 28
    return conv, op, used, conflict
```

> 注意：**单块内整片赋值是安全的**（行数由探测得出）（这是 PY 的 `Value2`，与 AirScript 的 `Value2` 是两套实现）。AirScript 那个「只认第一行」的坑不适用于 PY，但不代表可以乱写——PY 侧要求目标区域形状与数据形状严格一致。

**各项的判法表**（`record_sync.py` 的行为规范）：

| 明细结果 | 得分列 | 落表处理 |
|---|---|---|
| `NA` | 任意 | 得分写 `NA`，标准分不进分母 |
| `符合` / `合格` / `ok` | 空或 = 标准分 | 得标准分 |
| `扣分` / 空 | 空 | 全扣，得 0 |
| `扣分` | 0 < 得分 < 标准分 | 按填写的部分得分采信，计入「结果与得分不一致」告警 |
| `扣分` | 得分 ≥ 标准分 | 按扣分记 0，计入「结果与得分矛盾」告警 |
| 明细里没有该项 | — | 视为符合，得标准分 |

### 4.8 五条铁律（2026-11-18 修复，勿回退）

1. **一行一个扣分项，不是一行一张照片。** 照片可选，扣分项必记。按「有照片的项出行」会导致无照片的扣分项缺席 → `record_sync` 找不到该项 → 按「符合」给满分，等于白扣。
2. **「检查了、零扣分」必须留痕。** `deductions` 为空是正常业务结果，不是空包。`score_write.js` 写占位行，`read_check_zip.py` 会给旧包补占位行。
3. **块步长必须探测，探测失败必须拒绝写入。** 两种版式并存（79/78），写死任何一个都会逐站错位。
4. **未检查 ≠ 满分。** 本月无任何明细行的站，整块保持模板原样。
5. **明细的「月份」「表类型」「序号」都要校验。** 月份自动归一；表类型只接受空或「运营检查」；序号找不到对应项的扣分行会列进「扣分已丢失」告警。

### 4.9 手工上表时的硬性步骤（错了就白丢 28 分）

粘 `检查明细_导入行.tsv` 时，**那条「序号」为空、「检查项目」写「本项巡检未发现不符合项」的占位行必须一起粘进去**。

如果按「序号为空」把它过滤掉：
`record_sync` 在明细里就找不到这个站这个月 → 判定「未检查」 → 整块留空 → 该站**白丢运营段 28 分**。
**代码补不上这一层，只能靠操作纪律。**

| 缺什么 | 后果 | 补法 |
|---|---|---|
| `module.json5` 无 CAMERA 权限 | 申请直接被拒 | 加 `ohos.permission.CAMERA` + `reason: "$string:camera_reason"` + `usedScene` |
| 无运行时申请 | 没走 `abilityAccessCtrl` | 加 `ensureCamera()` |
| 无 `onPermissionRequest` | 网页权限请求**一律默认拒绝** | 重写，白名单只放 `ohos.permission.CAMERA` |
| 无 `onShowFileSelector` | **ArkWeb 没有默认实现**，`<input type=file>` 点了毫无反应 | 重写，按 `event.fileSelector.isCapture()` 分拍照/相册 |

```ts
.onPermissionRequest((event) => {
  let want: string[] = [];
  try {
    const all: string[] = event.request.getAccessibleResource();
    for (let i = 0; i < all.length; i++)
      if (all[i] === 'ohos.permission.CAMERA') want.push('ohos.permission.CAMERA');
  } catch (err) { want = []; }
  if (want.length === 0) { event.request.deny(); return; }
  this.ensureCamera().then((ok: boolean) => {
    if (ok) event.request.grant(want);
    else { event.request.deny(); this.toast('未授予相机权限，无法拍照'); }
  });
})
```

**鸿蒙专有的三个坑**：

| 坑 | 现象 | 解法 |
|---|---|---|
| SDK 26.0.0 未导出 `cameraPicker.PickerResultCode` | `ERROR 10505001 Property does not exist` | 写字面值 `r.resultCode === 0`，别用常量 |
| `PickerProfile` 是接口类型 | `new` 会报错 | 用对象字面量赋值 |
| `build_app.bat` 末尾有 `pause` | 非交互环境卡死 | 直接调 `hvigorw.bat` |

### 9.1 打分页 / 手机端

| 现象 | 原因 | 处置 |

### 9.2 云函数 / 中转

| 现象 | 原因 | 处置 |
|---|---|---|
| 任何请求都回 `{"errorMessage":"0 code exit unexpected","statusCode":443}` | 代码没加载起来（443 = UserCodeError）。绝大多数是浏览器拦剪贴板、编辑器里还是默认模板 | 改上传 zip，一次解决 |

| `Content length exceed sync content length [6291456]` | 照片太多超 6MB | 删图（前端已卡 5MB，一般走不到） |
| `没有收到参数（Context.argv 为空）` | 链路通了、令牌也对，是前端 payload 问题 | 抓请求体核对 |
| 函数 URL 响应带 `Content-Disposition: attachment` | 平台加的，浏览器直接打开会下载 | `fetch` 不受影响，不用管 |

```
2. 把 tools/airscript/record_migrate_80.py 整段贴进去
3. 保持 MODE = 'dry' → 点运行 → 只看日志，一格都不会改
   正常日志：
     本次处理 12 张表：2027-01、2027-02 …
     --- 2027-01 ---
       2027-01：30 块 · 待改 30 块 · 已是新口径 0 块
               （dry 模式，未做任何改动）
     dry 跑完：共需改 360 块。
4. 确认数字对（12 表 × 30 块 = 360 块），把 MODE 改成 'run' 再跑一次
5. 日志最后必须是「自查通过：30 块全部为 80 项」和「完成：应改 360 块，实改 360 块」
6. 对《考核记录_2026.xlsx》重复一次，但先设 TARGET_MONTHS = ['2026-12']
```

**脚本做了什么**

```
① 扫 A 列标题行，探测 30 个站块（不是 30 块就整张表跳过）
② 逐块读项数：73 才改，80 就跳过（幂等，重复跑不会多插行）
③ 从最后一个块往上改（★ 在上方插行会把它下面的块整体下移，必须倒序）
④ 在「合计」行之前插入 7 行
⑤ 把该块 A/B/C/D 四列（序号/大类/项目/标准分）按新题库整体重写
⑥ 改完自查：30 块是否都为 80 项、标准分合计是否 100
```

**插行用的是哪个方法**

金山 PY 的插行方法名各版本不一，脚本按顺序试四种，日志里会打印实际生效的那个：

```
Rows(at:at+n-1).Insert  →  Range(Aat).EntireRow.Insert  →  …Insert(1)  →  Rows(at).Insert
```

四个都不行时会打印「插行失败，本表中止」并保留已改的块，不会静默丢数据。

**配套：record_sync.py 已经能同时吃两种块**

改造前/后、2026 旧表/2027 新表，用同一份 `record_sync.py` 即可——它不再假定 73 或 80，
而是逐块找「合计」行来确定明细区间。回归测试见 `python tools/_t_record_layout.py`。

## 附录 B 这套架构的可复用模式

如果以后要再做类似的「现场采集 → 表格台账」系统，下面这套模式可直接照搬：

| 环节 | 模式 | 关键点 |
|---|---|---|
| 采集端 | 静态网页 + PWA | 零安装、Service Worker 离线、`localStorage` 存草稿 |
| 传输 | 无服务器云函数做中转 | 令牌只放服务端；函数无状态、不存数据 |
| 触发 | 表格自带脚本的 webhook | 表格本身就是「后端」，不用另建数据库 |
| 长任务 | 异步提交 + 轮询 | 绕开同步接口超时；超时返回 `pending` 而不是 `failed` |
| 附件 | `Range.InsertImage(base64)` | 不经过图床、不要授权、真图嵌格 |
| 幂等 | 「同站点同周期整体替换」 | 重复提交不会产生第二份，用户可放心重试 |
| 汇总 | 跨簿 PY 脚本 | 结构靠探测不写死；探测失败拒绝写入 |
| 定时 | AirScript 定时任务推 GitHub | 静态页直接读 JSON，无需 API |

**四条通用铁律**（踩出来的）：

1. **超时 ≠ 失败。** 只要请求可能已送达，就不能报「失败」，否则用户会重复提交。
2. **结构靠探测，不写死。** 版式多变时，探测失败宁可拒绝执行，也不能写错位置。
3. **「没数据」和「没检查」是两件事。** 零值是正常业务结果，缺失才是异常，两者必须能区分。
4. **沙盘测不出来的坑，只能真机验。** 批量赋值只认第一行、粘贴被拦、ROM 回 RESULT_CANCELED —— 全都是 mock 永远成功的场景。
